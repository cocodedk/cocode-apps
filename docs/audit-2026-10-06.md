## Inconsistencies found

1. No site or README links to F-Droid, including the three live apps.
2. Privacy: six apps have no live page; eight use flat `privacy.html`, one `/privacy/`; several index
   pages don't link it; lifemeter's page names `com.example.first`; persian-calendar's page calls the
   app "Persian Pro Calendar".
3. In-app: five About screens, five layouts; no privacy link; no update path except GitHub links.
4. Store listing: screenshots only in chess-puzzles; no icon or feature graphic anywhere; `en-US`
   only except guard-android; TMS and BabakPlayer have in-app languages without matching listings.
5. F-Droid readiness: fits-qr and Claude-Email-App take the version from an environment variable;
   Claude-Email-App has the foojay resolver and no `dependenciesInfo` off; three versionCode schemes;
   BabakPlayer's versionName is a bare integer.
6. Layout and naming: `docs/` + `pages.yml` (3 apps) vs `website/` + `deploy-pages.yml`; nine sites
   lack sitemap and robots; four lack a share image; three lack hreflang; download links split between
   `releases/latest` and `releases/latest/download/X.apk`; asset names vary in case; package prefixes
   `com.cocode`, `dk.cocode` and `dk.fits`.

## What the existing skills cover

- `android-setup`: release gate (privacy page + downloadable APK), version in `gradle.properties`,
  CI/release/Pages workflows with a stable asset, README, llms.txt, a bilingual site with SEO.
- `fdroid-release`: readiness, preflight, recipe, MR, pipeline watch, reviewer checklist (including
  "link F-Droid from README and site once accepted").
- Neither: store images and non-English listings, in-app About and privacy link, privacy pages for
  network-using apps, a shared install block, an automatic post-acceptance flip, a cross-app status
  table, one privacy path, one About and site layout.
